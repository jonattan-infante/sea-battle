  - **La regla:** sección «Deploys a producción» de `CLAUDE.md` (`CLAUDE.md:47–54`, en el árbol de trabajo).
  - **La barrera de GitHub:** el entorno `production` tiene ahora `can_admins_bypass: false` (lo leí por la API con un GET).
  - **La barrera de Claude Code:** `.claude/settings.json` deniega 17 patrones: cualquier comando con `pending_deployments`, las escrituras al entorno `production` y a los rulesets, `deploy.py` con `production`, las mutaciones de deploy de Railway, `railway up` y `railway redeploy`.
- **Nota:** como dice la propia regla, las barreras son una red de seguridad y no la garantía. Por ejemplo, `gh run cancel` (cancelar un deploy pendiente, que la regla también prohíbe) o llamar a `deploy()` de `railway_api.py` desde un script no coinciden con ningún patrón. Ninguna de las dos cosas sale en el plan de QA.

### O-25 · P3 (propuesta) · Si `gh release create` falla después de empujar el tag, la release no se crea nunca

- El job de prod mira solo si existe el tag (`ci.yml:130`). Si el tag se empujó (`:138`) y `gh release create` (`:139`) falla, la corrida siguiente ve el tag y sale sin crear la release.
- **Propuesta:** comprobar también la release (`gh release view "$tag"`) y crear solo lo que falte.
